# TuKios — Brief del proyecto para Claude Code

SaaS multi-tenant de gestión para kioscos/almacenes/minimarkets argentinos. Cada local tiene catálogo público + checkout propio, y un panel de gestión de stock/ventas.

## Stack

- Next.js (App Router) + TypeScript, un solo proyecto (público + panel + API routes)
- Tailwind CSS
- Drizzle ORM + Postgres (Supabase)
- Supabase Auth (dueño/empleados) + Supabase Storage (imágenes)
- Mercado Pago (Checkout Pro)
- Hosting: Netlify + Supabase (planes gratuitos, ambos permiten uso comercial)

## Arquitectura multi-tenant

- Cada tienda vive en `sulocal.tukios.com`. Proxy de Next.js (`proxy.ts`, función `proxy` — reemplaza a `middleware.ts`, deprecado desde Next.js 16) lee el header `Host`, extrae el subdominio, resuelve la tienda y sirve su catálogo.
- Panel de gestión en subdominio fijo separado: `panel.tukios.com`.
- Landing institucional del software en `tukios.com` (raíz).
- Admin interno (altas manuales, sin login de cliente) en `admin.tukios.com`, protegido con HTTP Basic Auth a nivel de proxy — ver "Onboarding de tiendas" más abajo.
- **Regla de oro:** casi toda query está filtrada por `tienda_id`. RLS en Postgres en cada tabla (no confiar solo en validación de la app). `tienda_id` siempre como primera columna en índices compuestos.
- Vista `productos_publicos` para el catálogo público: nunca expone `costo` ni `porcentaje_ganancia`.
- **Cualquier vista nueva del proyecto necesita revisar sus grants explícitamente después de crearla**, con una query contra `information_schema.role_table_grants` (filtrando por esa vista). El `ALTER DEFAULT PRIVILEGES` de `drizzle/0002_grants_authenticated.sql` le otorga SELECT/INSERT/UPDATE a `authenticated` automáticamente sobre cualquier tabla o vista nueva que cree el rol `postgres` en `public` — no asumir que una vista queda protegida solo porque no se le dio ningún GRANT explícito. Si la vista no debe ser visible para `authenticated` (por ejemplo porque, como `productos_publicos`, oculta columnas sensibles de la tabla base y además su dueño bypasea RLS), hace falta un `REVOKE` dirigido después de crearla — ver `drizzle/0004_revoke_authenticated_productos_publicos.sql` para el caso real que disparó esto.

### Estado de implementación

- **RLS (Row Level Security):** implementado y verificado — función `mi_tienda_id()` (SECURITY DEFINER) + policies de SELECT/INSERT/UPDATE (sin DELETE) por `tienda_id` en las 6 tablas, más los GRANT correspondientes al rol `authenticated`. Ver `drizzle/0001_rls_policies_aislamiento_tienda.sql` y `drizzle/0002_grants_authenticated.sql`.
  - ✅ **Resuelto** (antes prioritario, [issue #2](https://github.com/AgustinBenedetti/TuKios/issues/2) — "Empleado puede auto-asignarse el rol de dueño"): la policy de UPDATE en `usuarios` ya distingue dueño/empleado. Cualquier usuario puede editar su propia fila excepto el campo `rol`; solo un usuario con `rol = 'dueño'` puede editar filas ajenas de su tienda (incluido el `rol` de otros). Función auxiliar `mi_rol()` (mismo patrón SECURITY DEFINER que `mi_tienda_id()`). Ver `drizzle/0006_policy_update_usuarios_restringe_rol.sql` (incluye el análisis de por qué se resolvió con una sola policy en vez de varias) y `sql/verificacion_policy_update_usuarios.sql` para probarlo a mano.
  - Nota: la creación de la `tienda` en sí (fila en `tiendas`) sigue sin policy de INSERT — no hay ninguna definida a propósito (ver 0001). No es un problema: ese paso solo lo hace el flujo de onboarding descripto abajo, que corre enteramente con `service_role` (bypasea RLS by design), no con un usuario autenticado normal.
- **Trigger de sincronización `auth.users` → `usuarios`:** implementado — función `handle_new_auth_user()` (SECURITY DEFINER) + trigger `on_auth_user_created` (`AFTER INSERT ON auth.users`). Al hacer signup, crea automáticamente la fila correspondiente en `usuarios`, leyendo `tienda_id`, `nombre` y `rol` desde `raw_user_meta_data` (el `options.data` que se pasa a `supabase.auth.signUp()` / `auth.admin.createUser()`). Si falta alguno de esos tres campos en el metadata, el trigger rechaza el INSERT completo (revierte también la fila de `auth.users`, misma transacción) — no permite usuarios huérfanos. Ver `drizzle/0005_trigger_sync_auth_users.sql`. Probado con datos reales del flujo de onboarding (no solo inserts manuales) — ver más abajo.
- **Onboarding de tiendas (alta manual):** implementado — `admin.tukios.com` (`admin.localhost` en dev), route group `(admin)`, protegido con HTTP Basic Auth verificado en `proxy.ts` (credenciales en `ADMIN_BASIC_AUTH_USER`/`ADMIN_BASIC_AUTH_PASSWORD`, sin relación con usuarios de la app). Es la única forma de dar de alta una tienda hoy — no hay self-signup público todavía, esto es una herramienta interna para que el dueño del proyecto (Agustín) cargue clientes a mano.
  - Formulario (`app/(admin)/admin/`) → server action `crearTiendaYDueno` (`actions.ts`). Corre en el servidor únicamente: usa la service_role key vía `lib/supabase-admin.ts` (`import "server-only"` fuerza error de build si algún componente cliente lo importara por error), que nunca llega al navegador.
  - Paso a: `INSERT` en `tiendas` con el cliente de Supabase + service_role key (sin usuario autenticado en este flujo, es la única forma). Paso b: `auth.admin.createUser()` con `user_metadata = { tienda_id, nombre, rol: 'dueño', debe_cambiar_password: true }` — dispara el trigger de sincronización de arriba, que crea la fila en `usuarios` (no se inserta a mano a propósito). `debe_cambiar_password` no lo lee el trigger (solo lee tienda_id/nombre/rol), es exclusivo del flujo de login del panel — ver más abajo.
  - Si el paso b falla después de que el paso a ya creó la tienda, la action revierte el `INSERT` de `tiendas` (no deja locales huérfanos sin dueño).
  - Contraseña: se genera en el servidor (`crypto.randomBytes`, no un valor fijo) y se muestra una sola vez en pantalla para que Agustín se la pase al cliente a mano (WhatsApp, en persona) — se eligió esto en vez del email de invitación de Supabase para no depender de tener SMTP configurado todavía; el trade-off es que Agustín ve la contraseña en texto plano por un instante, aceptable para el volumen de altas manuales del MVP.
  - **Gap encontrado al construir esto (no antes documentado):** `service_role` nunca había tenido GRANT de tabla en ninguna de las 6 tablas (mismo problema que 0002 había resuelto solo para `authenticated`) — bypasea RLS, pero Postgres chequea privilegios de tabla ANTES de evaluar RLS, así que el primer `INSERT` real fallaba con "permission denied". Resuelto en `drizzle/0008_grants_service_role.sql`.
  - Verificado end-to-end contra datos reales (no solo `tsc`/lint): request HTTP real con y sin Basic Auth, server action real vía el proxy, service_role real, trigger real -- limpiado después, sin dejar datos de prueba.
- **Login del panel + cambio de contraseña obligatorio:** implementado — `panel.tukios.com` (`panel.localhost` en dev), dentro del route group `(panel)`. Como `proxy.ts` reescribe cualquier path de ese host a `/panel/*`, las páginas físicamente viven en `app/(panel)/panel/{login,cambiar-password}/` (no en `app/(panel)/{login,cambiar-password}/` -- un nuevo path público bajo panel.tukios.com necesita su carpeta espejada dentro de `app/(panel)/panel/`, no como hermana).
  - Librería: `@supabase/ssr` (paquete oficial de Supabase para sesiones SSR en Next.js App Router -- reemplazó a los viejos `auth-helpers`), confirmado contra la documentación oficial al construir esto, no asumido de memoria. `lib/supabase/server.ts` (Server Components/Actions, usa `cookies()` de `next/headers`) y `lib/supabase/proxy.ts` (proxy.ts, trabaja directo sobre `NextRequest`/`NextResponse`) son las dos mitades del mismo patrón `getAll`/`setAll` de cookies que pide el paquete -- no se puede compartir una sola porque `next/headers` no existe en el contexto de proxy.
  - Se usa `getClaims()`, nunca `getSession()`/`getUser()` a secas, para leer la sesión: `getSession()` decodifica el JWT sin verificar la firma (un token adulterado pasaría), `getClaims()` sí la verifica (localmente contra el JWKS cacheado del proyecto, o contra el servidor de Auth si el proyecto usa firma simétrica).
  - **Doble capa de protección, a propósito (ni proxy solo, ni layout solo):**
    - `proxy.ts` hace un chequeo **optimista** (solo lee/valida el JWT de la cookie, nunca pega contra `usuarios`) y centraliza los redirects para las tres rutas del panel: sin sesión → `/login`; con sesión y `debe_cambiar_password: true` fuera de `/cambiar-password` → `/cambiar-password`; con sesión y flag en `false` sobre `/login` o `/cambiar-password` → `/`.
    - Cada página protegida (hoy: `/panel`, `/panel/cambiar-password`) llama además a un chequeo **autoritativo** propio vía `lib/panel-auth.ts` (`requerirSesionPanel()` / `requerirSesionParaCambiarPassword()`). Se decidió explícitamente **no** resolver esto en un layout compartido de `(panel)`: la doc oficial de Next.js sobre autenticación advierte que un layout ya montado no se re-ejecuta en navegaciones client-side entre rutas que lo comparten, así que un chequeo puesto ahí puede no correr en cada cambio de página. Tampoco alcanza con dejarlo solo en `proxy.ts`: la propia doc de Proxy advierte que un cambio futuro en el `matcher` podría dejar de cubrir una ruta sin que sea obvio (mismo problema ya documentado para `admin.tukios.com`, ver `lib/admin-auth.ts`). Mismo criterio que "toda query filtra por `tienda_id`": la regla se aplica en el punto de uso, no se asume heredada de un padre.
  - **Bug real encontrado y corregido durante la verificación end-to-end (no antes documentado):** el JWT no se refresca solo después de `supabase.auth.updateUser({ data })`. Los claims (incluido `user_metadata.debe_cambiar_password`) quedan fijados en el momento en que el access token se firmó; cambiar el metadata en el servidor de Auth no reescribe el token ya emitido. Sin un refresh explícito, el usuario quedaba en loop infinito hacia `/cambiar-password` después de cambiar la contraseña con éxito (la cookie seguía teniendo el JWT viejo hasta que expirara solo, ~1h). Se arregló llamando a `supabase.auth.refreshSession()` inmediatamente después del `updateUser()` exitoso, en `app/(panel)/panel/cambiar-password/actions.ts` -- eso fuerza un token nuevo (con el metadata ya actualizado) y lo persiste en la cookie a través del `setAll` de `lib/supabase/server.ts`. Reproducido y confirmado el fix con un flujo HTTP real de punta a punta (login → cambiar-password → home → logout → re-login), no solo con llamadas directas al SDK.
  - `updateUser({ password, data })` hace **merge** de `data` contra el `user_metadata` existente (no lo reemplaza) -- confirmado empíricamente, no asumido: `tienda_id`/`nombre`/`rol` cargados en el onboarding quedan intactos al apagar `debe_cambiar_password`.
  - Placeholder post-login en `app/(panel)/panel/page.tsx` ("Bienvenido, estás logueado como {nombre}") con un botón de logout -- el contenido real del panel es un feature aparte, todavía no implementado.
- **Vista `productos_publicos`:** implementada — expone `id, tienda_id, categoria_id, nombre, foto_url, precio_final, disponible, codigo_barras` de `productos`, sin `costo` ni `porcentaje_ganancia`. Solo `anon` tiene GRANT SELECT sobre ella; `authenticated` no tiene ningún privilegio ahí (sigue usando la tabla `productos` completa, sin cambios). Ver `drizzle/0003_vista_productos_publicos.sql` y `drizzle/0004_revoke_authenticated_productos_publicos.sql` para el detalle y el porqué (vistas + RLS + bypass del dueño son un caso no obvio, vale la pena leer los comentarios antes de tocar esto). No filtra por `tienda_id`: eso queda para la query de la app (páginas del catálogo público, feature aparte, todavía no implementado).

## Modelo de datos (resumen — ver documento completo para detalle de tipos/índices)

- **tiendas**: subdominio (unique), nombre, logo_url, whatsapp, ubicacion, redes_sociales (jsonb), horario_atencion (jsonb), horario_delivery (jsonb, independiente del anterior), plan, activo
- **usuarios**: tienda_id, nombre, email, rol (`dueño` | `empleado`)
- **categorias**: tienda_id, nombre
- **productos**: tienda_id, categoria_id, nombre, foto_url, codigo_barras (unique compuesto con tienda_id), costo, porcentaje_ganancia, precio_final (auto-calculado, editable a mano recalculando el % hacia atrás), stock, disponible
- **ventas**: tienda_id, usuario_id (nullable), origen (`mostrador`|`online`), metodo_pago (`digital`|`efectivo`), metodo_entrega (`retiro`|`delivery`), cliente_nombre, cliente_apellido, cliente_telefono (obligatorios en ventas online, no en mostrador), cliente_calle/numero/barrio (solo si delivery), total, estado, creado_en
- **venta_items**: venta_id, producto_id, cantidad, precio_unitario (copiado al momento de la venta, no referenciado — es un registro histórico)

## Reglas de negocio clave

- Precio final = costo + costo×%ganancia. Si se edita el precio a mano, se recalcula el % hacia atrás. Sincronizados siempre entre sí.
- Checkout bloqueado fuera del horario de atención del local.
- Delivery puede tener su propio horario, más acotado que el del local.
- Costo/zona de envío no se gestiona en la app: se coordina por WhatsApp con el teléfono cargado en la compra.
- Sin seguimiento de estado de pedido en tiempo real en el MVP.
- Empleado puede: cargar stock, vender (caja básica), marcar pedidos online como completados, ver historial de ventas (sin reportes). Empleado NO puede: tocar precios/costos, ver reportes, cambiar configuración.
- Notificación de pedido nuevo: dashboard en tiempo real (Supabase Realtime) + email. WhatsApp pospuesto a v1.1 (Meta cobra por mensaje utility desde jul. 2025, no es $0).
- **Pendiente:** las columnas `cliente_nombre`, `cliente_apellido`, `cliente_telefono` (obligatorias en ventas online, no en mostrador) y `cliente_calle`, `cliente_numero`, `cliente_barrio` (obligatorias solo si `metodo_entrega` es `'delivery'`) hoy son nullable en el schema sin ningún enforcement — la base de datos permite cualquier combinación. Falta decidir, cuando se construya la lógica de ventas, si esto se garantiza con un CHECK constraint en Postgres o con validación en la capa de aplicación, y luego implementarlo.

## Alcance del MVP

Incluye: un local por cuenta, catálogo + checkout completo, carga de productos manual + escaneo de código de barras (NO importación masiva todavía), ventas de mostrador y online sobre el mismo stock, roles dueño/empleado, reportes básicos (ventas por período, más vendidos, stock bajo).

Explícitamente fuera del MVP: multi-sucursal, reportes de ganancia/margen, WhatsApp automatizado, zonas de delivery configurables, importación masiva, caja fiscal.
